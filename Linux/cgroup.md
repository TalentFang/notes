
简单来说，**cgroup v2 是 Linux 资源管理机制的“新一代架构”，而 v1 是“旧版本”。** cgroup v2 在 v1 的基础上进行了彻底的重构，以解决其多年积累的设计和功能问题，目前已成为主流，并且 Kubernetes 等容器生态已弃用 v1。

v1 和 v2 的核心区别，主要体现在以下几个维度：
## 1. cgroup v1 和v2的区别
### 1. 从“多棵树”到“一棵树”

这是两者最根本的不同，它决定了使用方式的简洁性和安全性。

*   **cgroup v1：多棵独立的树**：每个资源类型（如 CPU、内存）都有自己的、独立的控制树。一个进程可能同时属于 CPU 树上的某个节点和内存树上的另一个节点，管理起来复杂且容易出错。
*   **cgroup v2：单一统一的树**：所有资源控制器被整合到**一个统一的层级结构**中。一个进程只属于一个控制节点，所有资源的配置都在这里统一管理，逻辑清晰，行为更可预测。

### 2.  核心接口差别

由于架构不同，v1 和 v2 在具体配置接口上也发生了巨大变化，这也是你在配置 Kubernetes 时需要特别留意的。

| 功能维度 | cgroup v1 接口 | cgroup v2 接口 | 关键差异说明 |
| :--- | :--- | :--- | :--- |
| **CPU 权重（相对分配）** | `cpu.shares` (默认 1024) | `cpu.weight` (默认 100) | 语义相同，但**数值范围和默认值不同**，直接迁移需注意转换。 |
| **CPU 配额（硬性限制）** | `cpu.cfs_quota_us` / `cpu.cfs_period_us` | `cpu.max` | v2 将周期和配额合并到一个统一的 `cpu.max` 文件中，格式为 `$MAX $PERIOD`，配置更简洁。 |
| **内存控制** | `memory.limit_in_bytes` | `memory.max`, `memory.high`, `memory.low`, `memory.min` | v2 引入了更精细的**多级水位线**控制，从“一刀切”的硬限制，扩展到了包含软限制、保护值的精细化管理。 |
| **进程/线程管理** | `tasks` (线程粒度) | `cgroup.threads` (需开启线程模式) | v2 默认以**进程**为单位，支持更安全的**线程级控制**，但需要显式开启。 |
| **子系统（控制器）** | 每个子系统独立目录 | `cgroup.controllers`, `cgroup.subtree_control` | v2 通过这两个文件**动态管理子控制器**，父级必须显式声明允许子级使用哪些控制器，安全性更高。 |

### 3. v2 的主要优势

除了架构更清晰，cgroup v2 还带来了许多实际的功能增强：

*   **更安全**：支持更安全的子树委派，容器运行时可以在其 cgroup 下安全地创建子 cgroup，而不会影响根目录或其他部分。
*   **更强大**：引入了压力阻塞信息（Pressure Stall Information，PSI），能更准确地反映资源压力。
*   **更精准**：在不同类型的内存分配（如网络内存、内核内存）上实现了统一核算，避免了资源统计盲区。


## 2. cgroup v2的资源限制原理
### 2.1 核心行为：资源限制的“继承”与“级联”

**在 cgroup v2 下，父目录的资源限制会直接影响和包含子目录。**

这是一个非常关键的特性，也是 cgroup v2 统一层级结构带来的核心行为。简单来说，**子目录（子 cgroup）可用的资源，一定不会超过父目录（父 cgroup）所设定的上限。

如果把 cgroup 的层级想象成一个“企业预算”体系，那么：

*   **父目录是“总公司”**：它拥有总预算（例如，总内存限制为 10Gi）。
*   **子目录是“子公司”**：所有子公司的预算总和**不能超过**总公司的总预算。每个子公司自己的预算，也必须在总公司预算这个大框架内分配。

这意味着，**父目录的 `memory.max`、`cpu.max` 等限制，是所有子孙目录无法逾越的“天花板”**。

---

### 2.2 实际案例演示

假设你有如下 cgroup 层级：

```
/sys/fs/cgroup/
├── kubepods.slice/                    # 父目录，设置了 memory.max = 10Gi
│   ├── pod-1/                         # 子目录 1，设置了 memory.max = 8Gi
│   │   └── container-a
│   └── pod-2/                         # 子目录 2，设置了 memory.max = 4Gi
│       └── container-b
```

**实际效果：**

1.  **总上限生效**：`pod-1` 和 `pod-2` 的内存使用量之和，**永远不能超过**父目录 `kubepods.slice` 的 10Gi 限制。
2.  **子目录独立**：在 10Gi 的“天花板”下，`pod-1` 和 `pod-2` 各自有不超过 8Gi 和 4Gi 的限制。
3.  **动态约束**：如果 `pod-1` 已使用 8Gi，那么 `pod-2` 最多只能使用剩余的 2Gi（即使它自己的限制是 4Gi），因为父目录的总预算已耗尽。


## 3. 资源限制生效方法

在 cgroup v2 的统一层级树中，可以绑定到树分支上的核心对象是**进程（Processes）**。更准确地说，你可以将 **Linux 系统中的进程（以及它所属的所有线程）** 绑定到某个 cgroup 分支上，从而对该进程组施加资源限制。

所有进程默认都属于根 cgroup (`/`)。将其绑定到特定分支的操作，通常被称为“迁移（migrating）”。

### 3.1 如何绑定进程？

绑定的方法非常直接，核心操作是向目标 cgroup 目录下的 **`cgroup.procs`** 文件写入进程的 PID。

#### 示例：将 PID 为 33301 的进程绑定到 `/sys/fs/cgroup/MyGroups/g1/` 分支

```bash
echo "33301" | sudo tee /sys/fs/cgroup/MyGroups/g1/cgroup.procs
```

执行此操作后，PID 33301 这个进程，连同它所属进程的所有线程，都会被一同迁移到 `g1` 这个 cgroup 中。之后，这个进程组将受到 `g1` cgroup 下所有已启用控制器（如 `cpu.weight`）的限制。

你可以通过以下命令来验证是否绑定成功：
```bash
cat /proc/33301/cgroup
```
如果输出包含 `0::/MyGroups/g1`，则表明绑定成功。

### 3.2 绑定背后的“两步走”流程

要让上面的绑定命令生效，需要在创建 cgroup 分支时，先完成两个准备步骤，这让你可以清晰地理解其设计逻辑：

1.  **创建分支**：通过 `mkdir` 命令在统一层级树中创建一个目录，即一个子 cgroup。
    ```bash
    sudo mkdir /sys/fs/cgroup/MyGroups
    ```

2.  **启用控制器（Controller）**：这是 cgroup v2 的一个关键设计。新建的 cgroup 默认没有开启任何资源控制能力。你需要通过向 `cgroup.subtree_control` 文件写入 `+控制器名`，来启用特定的资源控制器（如 `cpu`），使其对**下一级子 cgroup**生效。
    ```bash
    # 在父级 MyGroups 目录下，为它的子目录（如 g1）启用 cpu 控制器
    echo "+cpu" | sudo tee /sys/fs/cgroup/MyGroups/cgroup.subtree_control
    ```
    只有完成了这一步，你才能在 `g1` 目录下看到并使用 `cpu.weight` 这类控制文件。

完成以上两步后，上述的绑定操作才能成功，并开始对进程组进行有效的资源限制。
