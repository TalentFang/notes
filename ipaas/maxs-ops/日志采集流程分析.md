## 一、概述

日志采集是一套 **「控制节点编排 + 各节点执行 + 回传打包」** 的 Ansible 体系，采用**手动触发**方式（无 crontab 定时调度）。

整条链路涉及的脚本与角色：

| 脚本/角色 | 路径 | 职责 |
|---------|------|------|
| 平台运维入口 | `tools/platform-ops.sh` | 命令分发，`logcollection` 子命令 |
| 采集入口脚本 | `tools/log_collection.sh` | 参数校验 + 磁盘预检 + 调 playbook |
| 日志大小预估 | `tools/log_collection_stat.sh` | 各节点预估日志大小，供磁盘判断 |
| 采集 playbook | `playbooks/common/41.log-collection.yml` | `hosts: all_server`，应用 log-collection role |
| 采集角色 | `roles/log-collection/` | 核心收集逻辑 |
| 收集工具脚本 | `roles/log-collection/templates/collect_logs_tool.sh.j2` | 下发到各节点，真正执行复制/过滤 |
| kafka 数据收集 | `roles/log-collection/templates/kafka_data_collect.sh.j2` | 收集 kafka 数据 |
| 配置映射表 | `roles/log-collection/vars/main.yml` | 定义各模块/组件/业务的日志路径映射 |

---

## 二、触发方式

**人工手动触发，无自动定时器**（全仓库无 crontab 引用 `log_collection.sh`）。

两种等效调用方式：

```bash
# 方式一：平台运维脚本（推荐入口）
/data/maxs-ops/tools/platform-ops.sh logcollection -a
/data/maxs-ops/tools/platform-ops.sh logcollection -m component -u redis
/data/maxs-ops/tools/platform-ops.sh logcollection -m business -u maxs-monitor -e

# 方式二：直接调用
sh /data/maxs-ops/tools/log_collection.sh -a
```

参数说明：

| 参数 | 含义 |
|------|------|
| `-a` | 收集全量日志（与 `-m`/`-u` 互斥） |
| `-m <类型>` | 模块类型：`system`/`component`/`business`/`data`（可逗号分隔多个） |
| `-u <单元>` | 指定单元，按模块类型不同枚举不同（可逗号分隔多个） |
| `-e` | 可选，仅收集错误日志 |

## 三、整体执行流程

```
platform-ops.sh logcollection [参数]
│
├── 1. main() 命令分发（case "logcollection"）
│       shift 后把剩余参数原样透传
│
├── 2. log_collection.sh
│   ├── getopts 解析参数
│   ├── validate_parameters 校验参数合法性
│   ├── log_collection_stat.sh 预估日志大小
│   ├── check_disk_threshold 磁盘空间预检（/data 75% 阈值）
│   └── ansible-playbook 41.log-collection.yml --extra-vars "..."
│
├── 3. roles/log-collection（每台 all_server 执行）
│   ├── 准备目录 + 下发 collect_logs_tool.sh
│   ├── 按模块过滤：system / component / business / config / data
│   ├── 调用 collect_logs_tool.sh 执行收集
│   └── 打包回传（非 master 节点 tar + fetch 回控制节点）
│
└── 4. 汇总打包（master 节点 run_once）
       解压所有 *.tar.gz → 清理 → 打包成 /data/cdt.tar.gz
```

## 四、模块收集逻辑

目录根为 `/data/cdt/{{ ansible_hostname }}`（每台节点一个子目录）。`main.yml` 中每个模块块用 `when` 条件过滤，只有命中的模块才执行：

| 模块 | when 条件 | 收集逻辑 | 执行节点 |
|------|----------|---------|---------|
| system | `'system' in module_type` | 遍历 `system_log_mappings`：`/var/log`、`os-release`、`hosts`、bash_history 等 | all_server |
| component | `'component' in module_type` | 按 `component_log_mappings` 收集指定组件 | all_server |
| business | `'business' in module_type` | 按 `business_log_mappings` + 动态发现 `/data/asap/logs` 子目录 | all_server |
| config | `'business' in module_type` | 导出 inventory + 各 namespace 的 ConfigMap/Service/Ingress | 仅 oper_master[0] |
| data | `'data' in module_type` | prometheus 数据 + kafka 数据 | 仅 oper_master[0] |

### 组件日志映射（component_log_mappings 节选）

| 组件 | 源路径 → 目标路径 |
|------|------------------|
| redis | `/data/asap/MAXS-CT/redis-maxs-ct/redis.log` → `component/redis/redis.log` |
| | `/data/asap/MAXS-CT/redis-maxs-ct/sen_data/sentinel_26379.log` → `component/redis/sentinel_26379.log` |
| mysql | `/data/comm/mariadb*/log` → `component/mysql` |
| es | `/data/comm/es/elasticsearch-7.17.5/logs` → `component/es` |
| kafka | `/data/comm/kafka_2.12-3.4.0/logs` → `component/kafka` |
| docker | `docker.service` → `component/docker`（systemd 服务） |

## 五、收集工具脚本（collect_logs_tool.sh.j2）

下发到各节点的核心工具，入参：`src` 源路径、`dest` 目标路径、`mode`（`error`/`full`）。

### 三种输入类型

1. **普通文件**：`full` 直接 `cp`；`error` 用 `grep -iE 'error|fatal|exception'` 过滤（`/data/install.log` 特殊：额外匹配 `result: 1`）
2. **目录**：递归 `find` 遍历所有文件
3. **systemd 服务**（`.service` 结尾）：用 `journalctl -u` 收集；`kubelet` 特殊——额外收集 `kubectl get pod -A`、`describe`、`top node/pod` 到 `pod.txt`/`top.txt`
4. **通配符**（`error.*.log`）：`shopt -s nullglob` 批量匹配，空目录自动清理

## 六、命令走查示例

以 `platform-ops.sh logcollection -m component -u redis` 为例：

```
1. 命令分发
   platform-ops.sh:3835 "logcollection" 分支
   → shift 后 sh /data/maxs-ops/tools/log_collection.sh -m component -u redis

2. 参数解析
   getopts → module_type=component, units=(redis), collect_all=false, error_logs=false

3. 参数校验
   component 在 valid_module_types 中 ✓
   redis 在 component 的 valid_units 白名单中 ✓

4. 磁盘预检
   log_collection_stat.sh /data/cdt component → 各节点预估大小
   check_disk_threshold → 已用 + 预估×1.5 是否超过 /data 的 75%

5. 执行 playbook
   ansible-playbook 41.log-collection.yml
     --extra-vars "collect_all=false module_type=component units=redis error_logs=false"

6. Role 模块过滤
   system 块 when=false 跳过
   component 块 when=true 执行：
     requested_units = ['redis']
     components_to_collect = ['redis']
     创建 /data/cdt/<hostname>/component 目录
     include_tasks component_log_tasks.yml, loop component=redis

7. 收集 redis 日志
   遍历 component_log_mappings[redis] 两个映射：
     sh /data/collect_logs_tool.sh '<src>' '/data/cdt/<hostname>/component/redis/<dest>' full
   mode=full → 直接 cp，产物：
     /data/cdt/<hostname>/component/redis/redis.log
     /data/cdt/<hostname>/component/redis/sentinel_26379.log

8. 打包回传
   非 master 节点：tar → fetch 回控制节点 /data/cdt/
   master 节点：run_once 解压所有 *.tar.gz → 清理 → 打包 /data/cdt.tar.gz

9. 清理
   log_collection.sh 成功分支 rm -rf /data/cdt，最终只留 /data/cdt.tar.gz
```

## 七、关键细节与潜在问题

1. **`error_logs` 判断不一致**：`main.yml` 中既有 `error_logs == 'true'`（字符串比较，如 `component_log_tasks.yml`），也有 `error_logs | default(false) | bool`（布尔判断）。入口脚本传的是 `error_logs=$error_logs`（true/false 字符串），需确认 Ansible 模板渲染后字符串 `'true'` 是否被转成布尔 `True`，否则 error 分支可能失效。

2. **`is_text_file` 已注释**（`collect_logs_tool.sh.j2` 约 138 行）：二进制文件现在也会被复制，注释说明是因为要收 prometheus 数据（prometheus 不跳过二进制）。

3. **component 模块静默跳过**：`component_log_tasks.yml` 的 `when: component in component_log_mappings` 意味着 `-u` 传了映射表不存在的组件会静默跳过，不报错（data 模块则是 `fail` 强校验）。

4. **config/data 模块只在 oper_master[0] 执行**，其余节点跳过。

5. **卸载清理**：`playbooks/destroy/25.files_and_vars.yml` 会删除 `/data/collect_logs_tool.sh` 和 `/data/file_upload_result.txt` 等下发产物。
