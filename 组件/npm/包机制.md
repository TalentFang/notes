### 1. 包的“身份证”：语义化版本（SemVer）

npm 包的所有版本号都遵循 **语义化版本规范**，格式是 `主版本号.次版本号.补丁版本号`（如 `2.1.0`），每一个数字变化都有严格含义：

| 版本号 | 变化规则 | 含义（对使用者影响） |
| :--- | :--- | :--- |
| **补丁版本** | 最后一位 +1（如 `2.1.0` → `2.1.1`） | **Bug修复**：修复了一个问题，但API和功能完全不变，可以放心升级。 |
| **次版本** | 中间位 +1（如 `2.1.0` → `2.2.0`） | **新增功能**：增加了新API，但旧的都还能用，向前兼容。 |
| **主版本** | 第一位 +1（如 `2.1.0` → `3.0.0`） | **破坏性变更**：API发生了不兼容的变化，升级可能导致项目报错，需谨慎。 |

在 `package.json` 中声明依赖时，我们会用符号来控制更新范围：
- `"lodash": "^4.17.21"` —— **插入符（^）**：允许更新到 `4.x.x` 范围内最新的次版本和补丁版本（即 `4.17.21` ≤ 版本 < `5.0.0`）。
- `"express": "~4.17.21"` —— **波浪符（~）**：更保守，只允许补丁版本更新（即 `4.17.21` ≤ 版本 < `4.18.0`）。
- `"react": "18.2.0"` —— 锁定精确版本，完全不动。

> 这种机制让你能**自动获得修复和新功能**，同时又不会突然收到一个大版本更新导致项目崩溃。

### 2. 依赖的“树”与“扁平化”：node_modules 的奥秘

当你运行 `npm install` 时，npm 会根据依赖树将包下载到 `node_modules`。

- **早期（npm v2）**：采取**嵌套结构**，每个包的依赖都装在自己的 `node_modules` 里。这会导致目录极深、大量重复，Windows 系统常因路径过长而报错。

- **现在（npm v3+）**：采用**扁平化（hoisting，提升）策略**。npm 会尽量把所有的包都安装到**最外层**的 `node_modules` 里，只有当**不同包需要同一个依赖的不同版本**时，才会把冲突的版本嵌套安装。

**举个例子**：项目依赖 `A` 和 `B`，它们都依赖 `lodash`，但 `A` 要 `lodash@4.x`，`B` 要 `lodash@3.x`。扁平化后，外层的 `node_modules` 放 `lodash@4.x`（因为版本更高），而 `B` 的 `node_modules` 里嵌套一个 `lodash@3.x`。这个算法叫**“将最常用的版本提升到顶层”**，大大节省了空间和加载时间。

### 3. 锁定“快照”：package-lock.json 的核心作用

`package-lock.json` 是 npm 自动生成的**锁定文件**，它记录了当时安装时**每个依赖的精确版本号**以及它们的依赖关系树。

**为什么需要它？** 因为 `package.json` 里写的是 `^4.17.21` 这样的范围，如果团队中不同成员在不同时间 `npm install`，可能会安装到不同的次版本（比如 `4.18.0`），导致代码行为不一致。`package-lock.json` 确保**任何人在任何机器上安装，得到的 `node_modules` 结构都完全一样**，是团队协作的“定海神针”。

> **注意**：它应该被提交到 Git 仓库，但永远不要手动修改它。

### 4. 常用命令速查表

| 场景 | 命令 | 说明 |
| :--- | :--- | :--- |
| **初始化项目** | `npm init -y` | 快速生成 `package.json` |
| **安装所有依赖** | `npm install` 或 `npm i` | 根据 `package-lock.json` 或 `package.json` 安装 |
| **安装生产依赖** | `npm install lodash` | 默认会写入 `dependencies` 字段 |
| **安装开发依赖** | `npm install --save-dev jest` | 写入 `devDependencies` 字段（测试、构建工具等） |
| **安装指定版本** | `npm install lodash@4.17.20` | 精确安装某个版本 |
| **全局安装工具** | `npm install -g typescript` | 安装为全局命令行工具 |
| **卸载包** | `npm uninstall lodash` | 从 `package.json` 和 `node_modules` 中移除 |
| **更新包** | `npm update lodash` | 在 `package.json` 允许的范围内更新到最新版本 |
| **查看过时包** | `npm outdated` | 列出所有有更新版本的依赖 |
| **查看全局包** | `npm list -g --depth 0` | 列出全局安装的顶层包 |

### 5. 自己发布一个 npm 包（简版流程）

如果你想把自己的代码分享给全世界的开发者，流程比你想象的要简单：

1.  **注册账号**：在 [npmjs.com](https://www.npmjs.com/) 注册。
2.  **登录**：在终端运行 `npm login`，输入用户名、密码和邮箱。
3.  **初始化包**：在项目根目录运行 `npm init`，按要求填写包名、版本、入口文件（`main`）等信息。
4.  **编写代码**：在 `index.js`（或你指定的入口文件）中 `export` 你的功能。
5.  **发布**：运行 `npm publish`。

> **注意**：包名不能和已有的重复。如果想发组织包（如 `@mycompany/my-package`），需先创建组织。

### 💡 最佳实践与避坑指南

- **永远把 `package-lock.json` 提交到 Git**，它是团队一致性的保障。
- **区分 `dependencies` 和 `devDependencies`**：不要把测试工具（如 Jest）装到 `dependencies` 里，这会无端增加生产环境包体积。
- **谨慎升级主版本**：升级主版本前，最好先阅读该包的 ChangeLog（更新日志），确认破坏性变更是否影响你的代码。
- **使用 `npm ci` 代替 `npm install`**：在 CI/CD（持续集成）环境中，`npm ci` 会根据 `package-lock.json` **精确且快速地**安装，比 `npm install` 更快更可靠。
- **管理 npm 源**：国内开发者可以使用淘宝镜像 `npm config set registry https://registry.npmmirror.com` 来加速下载。
