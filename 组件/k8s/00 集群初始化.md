## 1. 初始化过程
### kubeadm init 使用 kubelet 的具体步骤

1. **检查 kubelet 是否运行**：`kubeadm init` 执行前会检查 `kubelet` 是否已安装并处于运行状态。
    
2. **生成静态 Pod 清单**：`kubeadm` 根据配置生成 API Server、etcd、Controller Manager、Scheduler 等组件的静态 Pod 定义文件（YAML 格式），并写入 `/etc/kubernetes/manifests/` 目录。
    
3. **依赖 kubelet 启动静态 Pod**：`kubelet` 会持续监控 `/etc/kubernetes/manifests/` 目录，一旦发现新的静态 Pod 定义文件，就立即调用容器运行时（如 containerd）启动这些 Pod。
    
4. **等待控制平面就绪**：`kubeadm` 会轮询 API Server 的健康状态，确认控制平面组件已成功启动并运行。
    
5. **生成并配置 kubeconfig**：`kubeadm` 生成 `admin.conf` 等 kubeconfig 文件，供 `kubectl` 和后续组件使用，这些文件依赖 API Server 的地址和证书。

### 静态pod vs 动态pod
#### 1. 静态 Pod（Static Pod）

- **定义**：由 `kubelet` 直接管理，放置在 `/etc/kubernetes/manifests/` 目录下的 Pod。
    
- **网络模式**：静态 Pod 默认使用 **`hostNetwork: true`**，即**直接使用节点的网络命名空间**。
    
- **IP 来源**：它的 IP 就是**节点的主 IP**，没有经过 CNI 分配虚拟 IP。
    
- **例子**：`kube-apiserver-master-01` 的 IP 是 `192.168.111.190`，这正是节点 `master-01` 的 IP。
    

#### 2. 动态 Pod（普通 Pod）

- **定义**：通过 Deployment、StatefulSet 等控制器创建，由 API Server 调度到节点上的 Pod。
    
- **网络模式**：使用 **CNI 插件**分配独立的网络命名空间，每个 Pod 拥有一个独立的虚拟 IP。
    
- **IP 来源**：由 CNI 插件（如 Calico、Flannel）从 Pod 网络 CIDR 中分配，与节点 IP 不在同一个网段。
    
- **例子**：`coredns-9f86ffc8d-p5rhz` 的 IP 是 `113.122.184.99`，这是 Calico 分配的虚拟 IP。

### 第一部分：`InitConfiguration` (初始化配置)

这部分定义了**在当前节点上执行 `kubeadm init` 时的本地行为**。

- **`bootstrapTokens`**: 用于新节点加入集群的**引导令牌**。
    
    - `token`: 令牌字符串，格式为 `[a-z0-9]{6}.[a-z0-9]{16}`。后续其他节点需使用此令牌执行 `kubeadm join`。
        
    - `groups`: 令牌所属的 RBAC 组，这里指向 `kubeadm` 默认的节点引导组。
        
    - `ttl`: 令牌有效期，这里是 **24 小时**。过期后需要重新生成令牌才能加入新节点。
        
    - `usages`: 令牌的用途，包括 `signing`（用于签名客户端证书）和 `authentication`（用于身份验证）。
        
- **`localAPIEndpoint`**: 当前节点上 API Server 的本地监听配置。
    
    - `advertiseAddress`: API Server 对外广播的 IP 地址。这里使用了 **Ansible 变量 `{{ inventory_hostname }}`**，即当前节点的 IP。
        
    - `bindPort`: API Server 监听的端口，固定为 **`6443`**。
        
- **`nodeRegistration`**: 当前节点向集群注册时的设置。
    
    - `criSocket`: **容器运行时 (CRI) 的 socket 路径**。这里配置的是 `dockershim.sock`，这是 Kubernetes v1.24 前的旧模式，现在更常用的是 `containerd.sock`（路径为 `/run/containerd/containerd.sock`）。
        
    - `name`: 节点在集群中的名称，由 Ansible 变量 `hostname` 定义。
        
    - `imagePullPolicy`: 镜像拉取策略，设为 `Never` 表示**只使用本地已有镜像**，不向仓库拉取。这通常用于离线或完全本地化的部署环境。
        
    - `taints`: 节点污点配置。这里添加了 `PreferNoSchedule` 污点，意为**尽量避免**将普通 Pod 调度到该控制平面节点上。
        

### 🧠 第二部分：`ClusterConfiguration` (集群配置)

这部分定义了**整个集群**的全局设置，如证书、网络、存储等。

- **`apiServer`**: API Server 的专属配置。
    
    - `certSANs`: 证书的**主题备用名称 (Subject Alternative Name, SAN)**。这里通过 Jinja2 循环将 `{{ SERVER_VIP }}`（虚拟IP）、所有控制平面节点的 IP 和主机名都添加进去，确保通过任何这些地址访问 API Server 时证书都有效。
        
    - `timeoutForControlPlane`: 控制平面组件启动的超时时间，设为 **4 分钟**。
        
- **`certificatesDir`**: 所有 PKI 证书的存放目录，固定为 `/etc/kubernetes/pki`。
    
- **`clusterName`**: 集群名称，这里是 `kubernetes`。
    
- **`controllerManager` / `scheduler` / `dns`**: 这些字段留空或为 `{}`，表示使用 kubeadm 的默认配置。DNS 默认使用 CoreDNS。
    
- **`etcd`**: etcd 后端的配置。
    
    - 这里通过判断 `groups['inner_vip']` 是否为空，来决定使用 **外部 etcd** 还是 **本地 etcd**。
        
    - **外部 etcd**: 如果存在 `inner_vip` 组，则使用 `external` 模式，需指定 etcd 的所有 `endpoints` 地址以及用于 TLS 认证的 `caFile`、`certFile`、`keyFile`。
        
    - **本地 etcd**: 否则使用 `local` 模式，kubeadm 会在控制平面节点上部署一个 etcd 容器，`dataDir` 指定数据持久化目录。
        
- **`imageRepository`**: 镜像仓库地址。这里使用了变量 `{{ REGISTRY_IP }}`，表明集群会从一个**私有镜像仓库**拉取 Kubernetes 组件镜像，而不是默认的 `registry.k8s.io`。
    
- **`controlPlaneEndpoint`**: **控制平面的统一访问入口**。
    
    - 如果存在 VIP 组，则使用 `{{ SERVER_VIP }}:16443`（可能通过 HAProxy/Nginx 代理了 6443 端口）。
        
    - 否则直接使用 `6443` 端口。这个地址会被写入 kubeconfig 文件，供所有组件和用户访问集群。
        
- **`kubernetesVersion`**: 要安装的 Kubernetes 版本，这里是 `1.23.0`。
    
- **`networking`**: 网络插件 (CNI) 的配置。
    
    - `dnsDomain`: 集群内部 DNS 域名，默认为 `cluster.local`。
        
    - `podSubnet`: Pod 网络的 CIDR，由变量 `{{ CLUSTER_IPV4_IPV6 }}` 定义，CNI 插件（如 Calico）会使用这个网段分配 Pod IP。
        
    - `serviceSubnet`: Service 网络的 CIDR，由变量 `{{ SERVICE_IPV4_IPV6 }}` 定义，Kubernetes 会从此网段分配 Service 的 ClusterIP。
        

### 💡 关键设计思路

这份配置体现了几个典型的生产环境设计：

1. **高可用 (HA) 架构**：通过 `controlPlaneEndpoint` 结合 `certSANs` 中的 VIP，支持了多控制平面节点的部署。
    
2. **离线和私有化部署**：`imagePullPolicy: Never` 和自定义 `imageRepository` 表明环境可能无法访问公网，所有镜像已预先加载到本地私有仓库。
    
3. **外部 etcd 集群**：优先使用外部 etcd，将集群状态存储与 Kubernetes 控制平面解耦，提升了生产环境的稳定性和可维护性。
    
4. **配置模板化**：大量使用 `{{ ... }}` 变量，说明这是一个配合 **Ansible** 等自动化工具使用的动态配置文件。

重点解释几个文件

  1. kubeadm-flags.env — kubelet 启动时实际读取的参数：
  /etc/systemd/system/kubelet.service.d/10-kubeadm.conf中用EnvironmentFile=-/var/lib/kubelet/kubeadm-flags.env加载。
  kubelet 的 systemd 服务会 source 这个文件，所以改这个文件就能改 kubelet 的启动行为。Docker→containerd 迁移时就是要改这里的 --container-runtime-endpoint。

  pki/ — kubelet 自己的证书：
  - kubelet.crt / kubelet.key：kubelet 服务端证书。当 apiserver 访问 kubelet（kubectl logs/exec）时，kubelet 作为 HTTPS 服务端出示这个证书。这是自签的，不是 ca.crt 签发的。
  - kubelet-client-*.crt：kubelet 客户端证书。kubelet 访问 apiserver 时出示，这个是 ca.crt 签发的，CN 格式 system:node:<hostname>。

  kubelet 的 TLS 也是双向的：作为客户端访问 apiserver 时要验证，作为服务端被 apiserver 访问时也要验证。但两个方向的证书来源不同。

  pods/ — Pod 的根文件系统和挂载点，这就是 kubectl exec 进去看到的 /。Pod 删除时对应目录也会被清理。
