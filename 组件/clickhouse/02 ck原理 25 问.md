# ClickHouse 集群核心问题梳理

> 本文档整理自一次关于 ClickHouse 集群原理的问答，涵盖存储引擎、分片副本、Keeper 协调、分布式表及一致性等核心概念。

---

## 一、存储引擎基础

### 1. MergeTree、ReplicatedMergeTree、Distributed 的区别

| 名称 | 层级 | 是否存数据 | 核心职责 |
|------|------|-----------|---------|
| MergeTree | 本地表引擎 | 是 | 单机存储：分区、排序、稀疏索引、后台合并 |
| ReplicatedMergeTree | 本地表引擎 | 是 | 在 MergeTree 基础上增加副本，靠 Keeper 协调同步 |
| Distributed | 代理表引擎 | 否 | 分片路由、查询广播、结果汇总 |

三者关系：

```
Distributed（查询入口，不存数据）
    └── 指向各分片的 ReplicatedMergeTree（本地存储 + 副本）
            └── 底层基于 MergeTree（单机存储机制）
```

### 2. MergeTree 核心设计

- **LSM 树变体**：写入只追加，不修改已有数据。每次写入生成新的、不可变的 part，后台不断合并。
- **列式存储**：每列单独 `.bin` 文件存数据，`.mrk2` 文件存偏移标记。
- **分区键（PARTITION BY）**：逻辑分组，用于查询时分区裁剪。
- **排序键（ORDER BY）**：决定 part 内数据顺序，是稀疏主键索引的基础。
- **主键（PRIMARY KEY）**：默认等于排序键，不要求唯一，仅用于加速查询。
- **后台合并**：同分区内的小 part 归并成更大的 part，异步执行。

### 3. MergeTree 家族主要成员

- **ReplacingMergeTree**：合并时按排序键去重，保留最新一条。
- **SummingMergeTree**：合并时对指定列求和。
- **AggregatingMergeTree**：合并时按聚合函数合并中间状态。
- **CollapsingMergeTree**：通过标记位在合并时删除旧数据。
- **VersionedCollapsingMergeTree**：带版本号的 Collapsing 变体。

## 二、Part 与 Partition

### 4. part 和 partition 的关系

- **Partition**：逻辑分组，由 `PARTITION BY` 定义，用于数据裁剪，不直接对应磁盘目录。
- **Part**：物理目录，每次 INSERT 生成，实际存储数据。

一个 partition 可包含多个 part，后台合并的目标是让每个 partition 尽量只剩一个大的 part。

### 5. 一次 INSERT 生成几个 part？

- **本地表层面**：一次 INSERT 可能生成一个或多个 part。如果数据跨多个分区值，每个分区值各生成一个 part。
- **Distributed 表层面**：接收节点先按分片键拆分数据，转发给各分片本地表，每个分片**各自**生成 part，而非 Distributed 表本身生成 shard 个 part。

### 6. part 内部结构

以 Wide 格式为例，每个 part 目录包含：

- 每列一个 `.bin` 文件：存该列实际数据。
- 每列一个 `.mrk2` 文件：存数据块偏移标记。
- `primary.idx`：稀疏主键索引。
- `count.txt`、`checksums.txt` 等元数据文件。

所以 20 列的表，part 目录大致有 20 个 `.bin` + 20 个 `.mrk2` + 若干公共文件。

### 7. 后台合并后小 part 还在吗？

合并完成后：

1. 生成一个新的大 part。
2. 旧源 part 被标记为 `active = 0`（非活跃）。
3. 约 10 分钟后物理删除。

合并是“生成新的、替换旧的”，不是原地修改。

### 8. 合并的过程原理

- 本质：**多路归并排序**，把多个有序小 part 合并成一个更大的有序 part。
- 不跨分区，同分区内才合并。
- 合并时顺带执行引擎特有逻辑（去重、求和等）。
- 异步执行，不阻塞写入和查询。

### 9. 有序性如何保证？

- **part 内**：严格按 `ORDER BY` 有序。
- **同一 partition 内多个 part 之间**：无序，范围可能重叠。
- **合并后的 part**：内部依然严格有序。
- 跨 partition 查询不加 `ORDER BY`，返回顺序不确定。

## 三、分片与副本

### 10. 所有 shard 的 partition 一样吗？

- **逻辑上一样**：所有 shard 使用同一套建表语句，分区规则统一。
- **物理上各存各的**：每个 shard 只存属于自己的那部分数据，实际存在的 partition 数据不同。

### 11. shard 副本区分主从吗？都能读写吗？

- **Multi-Master 架构**，不区分传统主从。
- 可向**任意副本**写入，查询也可由任意副本独立完成。
- `system.replicas` 中的 `is_leader` 仅标记**后台合并任务的调度者**，不控制写入或查询。
- 不是“主从复制”，而是“多主 + 后台任务协调”。

### 12. 副本同步机制

异步拉取，不是推送：

1. 写入先落盘本地，生成新 part。
2. 将 part 信息注册到 Keeper/ZooKeeper 日志节点。
3. 其他副本监控 Keeper 日志变化，感知新数据。
4. 其他副本主动发起 HTTP 拉取，从写入副本下载 part 文件。

写入操作在本地完成后即返回成功，不等其他副本确认。

### 13. 同步不及时会影响查询结果吗？

**会。** 分两种情况：

- **查本地表**：连到哪个副本就查哪个副本的数据，未同步完则读不到新数据。这是最终一致性，延迟通常秒级。
- **查分布式表**：受 `max_replica_delay_for_distributed_queries` 控制，**默认 300 秒**。延迟未超 300 秒的副本仍可能被选中，读到旧数据；超过则跳过。

### 14. 如何保证写入后立刻可读？

使用 Quorum 写入：

```sql
SET insert_quorum = 2;
```

写入会等待指定数量副本确认后才返回成功。配合 `select_sequential_consistency = 1`，查询只返回已被 Quorum 确认的数据。代价是写入延迟变高。

### 15. 如何监控副本同步状态？

```sql
SELECT database, table, replica_name, absolute_delay, queue_size
FROM system.replicas
WHERE absolute_delay > 0;
```

- `absolute_delay`：副本落后秒数。
- `queue_size`：待处理同步任务数。

持续偏高说明副本同步跟不上。

### 16. part 均匀分布在 shard 上吗？

- **不一定均匀**，取决于分片键选择。
- 分片按行进行，分片键分布倾斜会导致数据倾斜。
- `rand()` 可大致均匀，但非物理强制均衡。
- 分片间不会自动迁移数据，加新分片后旧数据仍留老分片。

## 四、Distributed 表与查询

### 17. Distributed 表是谁在分发？

- **接收 INSERT 的节点（你连上的那个）**在分发。
- 写入时：逐行计算分片键，决定数据去向，转发到对应分片本地表。
- 查询时：把 SELECT 广播到所有分片，收集并合并各分片局部结果。

### 18. Distributed 表是依据 Keeper 选分片选副本吗？

**不是。**

- **选分片**：INSERT 时根据分片键本地计算，Keeper 不参与。
- **选副本**：SELECT 时根据 `load_balancing` 策略（默认 `random`）选择，同样不查询 Keeper。
- Keeper 主要配合分布式 DDL（`ON CLUSTER`）及让 Distributed 表知道集群拓扑。

### 19. 查询时 partition/part 如何组织成完整数据？

不是物理拼接，而是按需读取、局部计算、最后合并：

1. **分区裁剪**：根据 WHERE 条件跳过不相关 partition。
2. **选择副本**：每个分片内选一个可用副本读取。
3. **局部计算**：各分片在本地 part 上独立执行，算出部分结果。
4. **结果汇总**：Coordinator 收集所有分片部分结果，合并返回。

磁盘上不存在把全量数据拼在一起的文件，完整数据是查询时动态聚合出来的视图。

### 20. 合并期间有查询会怎样？

- **查询会读小 part**：查询总是针对查询开始时已存在的所有 part 执行。
- **不影响合并**：合并异步进行，不阻塞前台查询；查询也不阻塞合并。
- 两者可安全并发执行。

## 五、Keeper 与副本协调

### 21. Keeper 的作用只是协调副本吗？

不只是。Keeper 是**高可用协调中心**，职责包括：

- **副本协调**：副本通过 Keeper 感知变化，不直接通信。
- **分布式 DDL**：让建表语句在所有节点同步执行。
- **分布式表元数据追踪**：知道哪些分片可用。

### 22. Keeper 在副本中的具体角色

- 不存业务数据，只存副本协调所需元数据。
- 记录哪个副本是 Leader、复制日志队列、已同步进度、分布式 DDL 执行队列、副本只读状态。
- 3 节点 Keeper 集群通过 Raft 协议选举 Leader，多数节点存活即可工作。
- Keeper 不可用时，副本进入只读模式，已有数据仍可查询。

## 六、集群架构示例（3 节点）

### 23. 3 节点 ClickHouse 集群典型拓扑

**2 分片 × 2 副本**（生产推荐）：

| 分片 | 副本 1 | 副本 2 |
|------|--------|--------|
| shard 1 | node1 | node2 |
| shard 2 | node2 | node3 |

`node2` 同时承担 shard 1 的副本和 shard 2 的副本，是 3 节点做 2×2 副本的典型折中。

### 24. 3 节点的局限

- **容错能力有限**：只能容忍单节点故障。node2 宕机后，再宕任一节点会导致某分片完全不可用。
- **node2 压力偏大**：同时承载两个分片数据，磁盘和 CPU 负载可能更高。
- **不推荐 3 分片 × 1 副本**：无冗余，任一节点宕机即丢该分片数据。
- **跨分片 JOIN**：默认拒绝，需显式用 `GLOBAL JOIN` 或 `GLOBAL IN`。

### 25. 写入与查询完整流程

**写入**：

1. Distributed 表按分片键计算数据去向。
2. 发往该分片的某个副本。
3. 副本写入本地 ReplicatedMergeTree 表，通过 Keeper 同步日志给其他副本。
4. 其他副本拉取日志、回放，完成同步。

**查询**：

1. Distributed 表向各分片发查询。
2. 每个分片选一个可用副本读取。
3. 各路结果返回，Distributed 表合并输出。

## 附：常用排查 SQL

```sql
-- 查看集群拓扑
SELECT cluster, shard_num, replica_num, host_name, port
FROM system.clusters WHERE cluster = '集群名';

-- 查看副本同步状态
SELECT database, table, replica_name, absolute_delay, queue_size, is_readonly
FROM system.replicas WHERE absolute_delay > 0;

-- 查看 part 信息
SELECT database, table, partition, name, active, rows, bytes_on_disk
FROM system.parts WHERE active = 1;

-- 查看正在进行的合并
SELECT database, table, elapsed, progress, num_parts
FROM system.merges;

-- 查看当前查询
SELECT query_id, user, elapsed, read_rows, memory_usage, query
FROM system.processes;
```
